# Git authoring and publication

For a project bound to a Git repository, editor changes are saved to a stable `range42-ui/<project-id>` working branch. Save and the debounced autosave update this branch, record its commit SHA, and preserve the configured base branch. If the connected account cannot write to the repository, Save creates or reuses its verified fork and returns the actual repository binding for subsequent saves and backend registration. Authored files from the Config tab are saved beneath the project's subdirectory and restored from the saved file list in `meta.json`.

Variable overrides are included in `overlay.json`. Saves and publication within
the editor session share a queue for each repository branch so their writes do
not overlap. Reloading a direct project URL restores the locally persisted
project and its Git binding.

Deploy saves the current project snapshot and registers its actual repository binding with the selected backend before opening the deployment form. The deployment receives that working branch commit SHA; merging is not required. If the project changes while saving or loading the launcher, deployment waits for another save. The form creates the deployment, and the detail page provides deployment preflight, warning acknowledgment, and an explicit Start action. Pinned concrete scenarios use deployment preflight directly instead of the older catalog-overlay validator. The editor's Repository and Scenario controls provide the [concrete scenario authoring workflow](concrete-scenario-authoring.md).

Publish opens a file preview and allows several explicit destinations. GitHub, GitLab and Gitea destinations can each use a pull request or direct publication to their selected branch. For example, the same saved snapshot can become a pull request in a public catalog and a direct update in a private catalog. Repository visibility does not choose the publication policy. Each destination has a separate publication branch and result; a failed destination can be retried independently.

Pull request destinations explicitly choose automatic fork fallback, always using a fork, or requiring upstream write access. An optional destination selects an organization or GitLab group/subgroup; leaving it empty uses the connected account. Fork contributions write a dedicated branch in that verified fork and open the review against the selected upstream repository and branch. The provider verifies the fork relationship and write access before any content write; an unrelated same-named repository is rejected. Direct destinations always require upstream write access. Republishing reuses only an open review with the exact source repository, contribution branch and target branch.

Publication results persist their destination and commit SHA. Check merge status reloads provider permissions and checks; Merge reviewed commit supports merge or squash and rejects a contribution changed since publication. Providers enforce their branch protections on the final request. GitHub and Gitea can merge upstream changes into an existing contribution branch without rewriting history. GitLab creates a reverse cross-project merge request from the upstream branch into the writable fork contribution branch for review and conflict resolution. This works even when the fork has not fetched the latest upstream commit. After any update, inspect the contribution and publish the saved snapshot again before attempting the final merge.

GitHub, GitLab and Gitea save and publish all changed files in one commit. Rejected atomic commits are never retried as separate file writes. GitHub advances the branch without force; GitLab and Gitea preserve per-file concurrency checks. Retries reuse the saved checkpoint and skip identical files. The legacy adapter fallback still reports partial writes for providers without the batch capability. New component publication checks existing destination directories and files, and refuses to overwrite a different component or draft.

Publishing credentials are configured separately for the selected Git sources. Repository connection offers an explicit opt-in to store the supplied credential on the selected backend catalog source for private cloning; this updates the credential used by other projects sharing that source. The password field is cleared after a successful connection. Stored credentials are only used when the project connection matches its registered source provider and URL. Provider connections are captured before publication begins, so changing the selected backend during a request cannot substitute another source's credentials.

## Current boundaries

- Scenario generation supports explicitly configured VMs with declared network interfaces, SDN or existing bridges, and text or binary file copies, text scripts/playbooks and verified bundle imports. Binary files use the limits and byte-preserving storage described in [binary scenario files](binary-scenario-files.md). Other canvas kinds and legacy attachments block generation until converted; automatic team replication and template creation remain separate work.
- The new component form authors Ansible roles under `02_ansible_layer/admin/roles/<category>.<action>.<target>/`. Other component kinds need their own naming and file-generation forms.
- Organization/group forks require permission to create repositories in the selected namespace. Fork imports are asynchronous: a preparing fork reports an actionable retry message. New branches start from the selected upstream commit; if an older fork lacks that commit, synchronize its base on the provider before retrying. Existing contribution updates preserve history and report conflicts; no branch is force-reset. Gitea does not offer a compare-and-swap parameter for its update endpoint, so its update uses a head precheck plus a normal merge. GitLab synchronization remains a separate review rather than an automatic merge.
- GitLab project access tokens are scoped to one project and cannot create cross-project merge requests. Use a credential with access to both review destinations, such as the connected personal account token. Provider permission failures remain visible and never trigger a force push. See [GitLab project access tokens](https://docs.gitlab.com/user/project/settings/project_access_tokens/).
- Backend cloning credentials and browser publishing credentials have separate storage. Private forks need backend read access: opt in during repository connection or configure the backend source credential separately. No browser token is silently sent to the backend.
- Concrete configure and VM teardown actions use scoped preflight and explicit entrypoints. Configure can use a newer saved content revision while retaining the original VM/network/inventory definitions. Reset and rollback are not generated by this authoring form.
- Deployment metadata, preflight, attempts, cancellation and event streaming use the selected backend. Some older deployment action dialogs still use their legacy routes for legacy scenarios.

## Provider API references

The implementation follows the providers' official REST APIs: [GitHub forks](https://docs.github.com/en/rest/repos/forks#create-a-fork), [GitLab project forks](https://docs.gitlab.com/api/project_forks/), and [Gitea forks](https://docs.gitea.com/api/1.24/operations/create-fork/). GitLab cross-project reviews set the upstream `target_project_id` through its [merge request API](https://docs.gitlab.com/api/merge_requests/).

Atomic writes use [GitHub trees](https://docs.github.com/en/rest/git/trees#create-a-tree), [commits](https://docs.github.com/en/rest/git/commits#create-a-commit) and [non-forced references](https://docs.github.com/en/rest/git/refs#update-a-reference), [GitLab commit actions](https://docs.gitlab.com/api/commits/#create-a-commit), and [Gitea multi-file changes](https://docs.gitea.com/api/1.24/operations/repo-change-files/).

Review, merge and branch synchronization follow [GitHub pull requests](https://docs.github.com/en/rest/pulls/pulls), [GitLab merge requests](https://docs.gitlab.com/api/merge_requests/), [Gitea merges](https://docs.gitea.com/api/operations/repo-merge-pull-request/) and [Gitea contribution updates](https://docs.gitea.com/api/operations/repo-update-pull-request/).

Live provider results, isolated repositories and cleanup notes are recorded in [provider acceptance, 2026-09-10](provider-acceptance-20260910.md).
